# 状态机设计

## 设计约束

1. 外门和内门绝不能同时物理打开；
2. 内门是食物访问的安全边界；
3. 身份或占用有任何歧义，内门保持关闭；
4. 遇到遮挡或执行器故障时，优先保证宠物机械安全；
5. 门状态必须来自限位开关，不能只依赖执行器命令；
6. RFID 授权会被锁存为短时有效的“通行令牌”，宠物进入缓冲舱后不要求 RFID 持续可见。

## 顶层状态

```text
BOOT
  -> HOMING
  -> IDLE
  -> AUTH_PENDING
  -> OUTER_OPENING
  -> ENTRY_WAIT
  -> OUTER_CLOSING
  -> CHAMBER_VERIFY
  -> INNER_OPENING
  -> FEED_ENTRY_WAIT
  -> INNER_CLOSING
  -> FEEDING
  -> EXIT_SEQUENCE
  -> IDLE

在进入食物侧前中止：
  -> RECOVERY_OUTER_OPENING
  -> IDLE

任意运行态
  -> SAFE_FAULT
```

## BOOT

执行：

- 初始化 GPIO 与总线；
- 加载持久化配置；
- 恢复喂食账本；
- 初始化 RTC 和传感器驱动；
- 请求双门归零。

## HOMING

- 通过限位建立外门和内门的真实位置；
- 确认两扇门都能回到已知安全关闭状态；
- 归零失败则进入 `SAFE_FAULT`。

## IDLE

要求：

- 两扇门均确认关闭；
- 等待新的、已知的 RFID 身份；
- 同时必须存在该宠物可用的喂食会话。

## AUTH_PENDING

只有已知且当前允许喂食的宠物可以通过。

以下情况拒绝：

- 在真正开始通行前 RFID 已消失 / 失效；
- 未知 Tag；
- 当前时间不允许该宠物进食；
- 没有可用 meal/session；
- 授权超时。

通过后，将对应 `PetId` 锁存为本次通行身份。

这个通行令牌允许宠物进入缓冲舱后暂时丢 RFID，因为 RFID 只负责回答“是谁”，不能证明物理空间中只有一只动物。

## OUTER_OPENING

前置条件：

- 内门已确认关闭；
- 外门当前已确认关闭；
- 外门门槛安全。

下发开外门命令，并等待 open limit 确认。

## ENTRY_WAIT

等待授权宠物完整进入认证缓冲舱。

只有满足：

```text
occupancy == exactly one plausible pet
AND chamber mass matches authorized pet
AND outer threshold is clear
```

才允许进入外门关闭阶段。

出现以下情况直接中止并向外侧恢复：

- 怀疑存在两只宠物 / 尾随；
- 占用结果为 Ambiguous；
- 必要传感器失效；
- 进入超时。

## OUTER_CLOSING

只有外门光幕清空后才允许关门。

如果关门过程中外门门槛再次被遮挡：

- 当前授权失效；
- 明确撤销关闭并反向打开外门；
- 进入 `RECOVERY_OUTER_OPENING`；
- 禁止直接继续打开内门。

外门 closed limit 确认后进入 `CHAMBER_VERIFY`。

## CHAMBER_VERIFY

这是最关键的安全检查点。

只有同时满足：

```text
存在有效的通行授权令牌
AND 喂食会话仍有效
AND 外门已确认关闭
AND 内门已确认关闭
AND 外门光幕清空
AND 内门光幕清空
AND 缓冲舱估计只有一只宠物
AND 缓冲舱重量符合授权宠物
AND 必要占用传感器均健康且数据新鲜
```

才允许开内门。

V1 不采用多数投票，只要关键证据冲突就失败关闭。

## INNER_OPENING

只有 `CHAMBER_VERIFY` 通过才能进入。

整个阶段外门必须持续保持物理关闭确认。

## FEED_ENTRY_WAIT

等待宠物从认证缓冲舱进入进食舱。

第一版可将：

```text
认证舱为空
AND 内门门槛清空
```

作为宠物完成跨越的证据。

## INNER_CLOSING

只有内门门槛清空才允许关门。

如果关门过程中内门门槛重新被遮挡：

- 重新打开内门；
- 返回 `FEED_ENTRY_WAIT`；
- 禁止继续施加关门力。

内门 closed limit 确认后进入 `FEEDING`。

## FEEDING

此时宠物已经进入封闭进食舱。

该状态后续负责：

- 允许正确粮仓出粮；
- 记录食盆进食前 / 中 / 后重量；
- 限制本餐最大份量；
- 判断何时完成进食。

当前固件安全核心暂时在这里结束，完整的 meal completion 和反向退出流程属于下一阶段。

## EXIT_SEQUENCE

用于宠物吃完后的反向双门通行。

仍必须保持：

```text
NOT (outer_open AND inner_open)
```

食物侧必须先重新封闭，才能向外侧开放。

## RECOVERY_OUTER_OPENING

当宠物还未到达进食舱、本次进入尝试已经失败时使用。

规则：

- 内门必须确认关闭；
- 当前授权令牌立即失效；
- 打开外门，让缓冲舱中的动物全部退回外侧；
- 等待缓冲舱为空；
- 光幕清空后再关外门；
- 外门 closed limit 确认后返回 `IDLE`。

尾随场景下，不尝试猜测“哪一只该留下”，而是全部退回重新认证。

## SAFE_FAULT

典型触发：

- 两扇门同时物理开启；
- 双门归零失败；
- 门移动超时；
- open / closed limit 同时触发；
- 不可恢复执行器故障；
- 违反硬互锁。

缓冲舱验证阶段的传感器故障，如果还能安全向外侧恢复，优先走 `RECOVERY_OUTER_OPENING`；机械矛盾和互锁破坏则锁存 `SAFE_FAULT`。

优先级：

1. 不夹 / 不困宠物；
2. 不让错误宠物接触食物；
3. 记录并上报故障。

第一版不实现 `SAFE_FAULT` 自动恢复。

## 防尾随场景

### A：授权宠物单独进入

预期：关外门 → 二次验证 → 开内门。

### B：第二只宠物紧跟进入

可能证据：

- ToF 检测到 >=2 clusters；
- 地板重量超出授权宠物合理范围；
- 未来双 RFID Reader 检测到多个 Tag；
- 门槛长期被占用。

预期：内门保持关闭，授权作废，打开外门让全部宠物退出。

### C：第二只宠物只把头 / 身体留在门口

预期：外门禁止继续关闭，反向打开并取消本轮通行。

### D：两只宠物在 ToF 上重叠成一个目标

预期：重量等其他证据仍必须一致。无法证明“只有一只合理授权宠物”时，归类为 Ambiguous 并拒绝。

### E：授权宠物进入后 RFID 暂时消失

预期：不因瞬时丢 Tag 直接失败。继续使用已锁存的通行身份，但开内门前仍必须通过 ToF、称重、光幕和门状态核验。

## 持久化要求

至少保存：

- meal/session ID；
- pet ID；
- 计划喂食窗口；
- 已经出粮的重量；
- 会话完成状态。

绝不能把“某个门命令已经下发”持久化成“门已经物理到位”。
